# UX цепочек Batch / Recorder / Worklog / Jira transfer

2026-09-09. Read-only аудит по текущим HTML, обработчикам и lifecycle-контрактам после F01–F12. Полная architecture.md прочитана в исходном аудите; действующие разделы Batch, Worklog/Jira и Traffic Recorder перечитаны перед этим проходом. Ни интерфейс, ни код не изменялись. Внешние POST, авторизованные сайты и общий live profile не использовались. Это оценка доказуемых цепочек/подписей, не отчёт о визуальном user testing.

## 1. Jira transfer: «Отмена» означает выполнить копирование

**Путь:** текущая задача Jira → Popup «Jira» → «Копирование/перенос WorkLog в другую задачу» → prompt «В чьих записях будем искать?» → prompt с ключом назначения → confirm «Продолжить?» → confirm «Что делаем с исходными записями?», где **ОК = перенести, Отмена = скопировать**.

**Неудобство:** четыре последовательных диалога не дают одновременно проверить источник, автора, назначение и действие. В последнем диалоге обычное желание отменить приводит к внешнему действию — копированию. Фильтр автора ищет в имени/email/key, но перед запуском показывается только число совпадений, без списка людей, дат и часов. Ошибка ключа/автора завершает цепочку, и повтор начинается с первого prompt.

**Проще:** одна форма «Источник → Назначение», явный выбор «Копировать / Перенести», поиск автора с результатами и краткая таблица найденных записей/итог часов. После чтения API — одна итоговая кнопка «Скопировать N записей» либо «Перенести N записей»; отдельная «Отмена» всегда закрывает форму. Сохранять введённый черновик при ошибке поиска. После выполнения оставлять итог с частичными ошибками и ссылкой на задачу назначения вместо единственного alert «Обновите страницу».

**Зависимости:** `pages/popup/popup.html:284` (вход); `pages/popup/popup-jira.js:25` (prompts), `:67` (substring matching автора), `:86`–`:87` (две confirm), `:131` (финальный alert). Исполняемая функция работает внутри активной Jira-страницы; новый UI должен передавать уже выбранные параметры этому владельцу, сохранив origin/context-path checks, полную pagination и удаление только после успешного копирования. Это новая UX-находка, не повтор исправлений F01–F12.

## 2. Batch Series: пользователь подтверждает выбор и затем вручную запускает техническую подготовку

**Путь:** Popup «Grafana» → «Массовый сбор» → «Открыть панель сбора» → «Фильтр линий (Series)» → «ID панелей» → список с названиями → «Использовать выбранные» → **«Подготовить выбранные панели»** → фильтры/периоды → «Запустить сбор только по фильтрам (Series)».

**Неудобство:** «ID панелей» на самом деле открывает полноценный выбор панелей. После «Использовать выбранные» выбор ещё не готов к запуску; обязательна дополнительная кнопка, которая не предлагает нового решения, а только загружает definition/query signatures. Можно заполнить все фильтры и нажать старт, получив «Нет панелей для сбора», хотя панели уже были выбраны в модальном окне.

**Проще:** назвать вход «Выбрать панели»; после «Использовать выбранные» автоматически выполнять подготовку с явным статусом «Подготовка 3 панелей…». Кнопку запуска делать доступной после успешной подготовки, рядом показывать число панелей и ошибки конкретных панелей. При ошибке оставить отдельное действие «Повторить подготовку», а не требовать его для каждого успешного выбора.

**Зависимости:** `pages/batch/batch.html:132`, `:145`, `:283`; `batch-panel-picker.js:143`/`:158` (apply только сохраняет IDs и открывает кнопку подготовки); `batch-series-discovery-controller.js:200`/`:215` (подготовка); `batch-series-run-controller.js:62` (run читает готовые cards). Связать picker completion с существующим владельцем подготовки, сохранив F03 generation/URL/selection guards и отдельный явный старт захвата.

## 3. Batch: «Фильтр линий» выглядит дополнением общих настроек, но является вторым самостоятельным запуском

**Путь:** «Настройки сбора» → URL, диапазоны, «Правила обработки панелей» → «Фильтр линий (Series)» → повторные URL/периоды либо «Подставить URL и временные срезы из настроек сбора» → собственные тема/compact/режим → старт.

**Неудобство:** вкладка названа фильтром, хотя это отдельный workflow с отдельным URL, выбором панелей и кнопкой запуска. Копирование URL/времени разовое; последующее редактирование первого набора не синхронизирует второй. Подсказка «общие настройки дашборда игнорируются» не объясняет исключение: Series фактически загружает общие сохранённые **правила обработки панелей** для своего URL. Редактор этих правил находится только на первой вкладке. Дополнительно «Запустить сбор всего Дашборда» остаётся той же подписью при whitelist/blacklist, хотя будут собраны только отфильтрованные панели.

**Проще:** общий блок «Дашборд / Периоды / Панели», затем режим результата «Снимки панелей» или «Снимки выбранных серий». Если нужны независимые настройки двух сценариев, сохранить их, но назвать вкладки этими режимами и явно предложить «Использовать URL и периоды первого режима» / «Задать отдельно». В каждом режиме показать применяемые правила и ссылку «Изменить правила этого дашборда». Кнопка старта — «Собрать выбранные панели» с количеством; короткая сводка перед запуском: панели, периоды, тема, compact и правила.

**Зависимости:** `pages/batch/batch.html:37`, `:112`, `:141`, `:222`, `:246`; `batch-page-controller.js:147` (разовое копирование); `batch-series-run-controller.js:81`, `:187`, `:230` (общие правила реально применяются); `batch-main-run-controller.js:75` (whitelist/blacklist). Общие inputs можно согласовать на уровне page/state, не объединяя lifecycle main/Series. Для compact размер пока берётся из общих настроек (`batch-operation-controller.js:44`); в сводке полезно показывать фактический размер, а не отправлять пользователя искать его в Options.

## 4. Worklog: контекст Jira и путь восстановления авторизации находятся вне рабочего окна

**Путь:** Popup «Jira» → «Открыть WorkLog» → «Не авторизован» или «Ошибка связи» → единственное локальное действие «Проверить». Для смены сервера/часового пояса надо отдельно открыть настройки расширения → Jira → «Базовый URL Jira» / «Часовой пояс для списания времени», затем вернуться в таблицу.

**Неудобство:** таблица не показывает, на какой Jira и в каком часовом поясе будет создан worklog. «Проверить» повторяет запрос, но не предлагает вход и не объясняет, где исправить сервер. Настройки считываются в начале документа, поэтому после их изменения уже открытое окно не показывает, что продолжает пользоваться прежним контекстом. Новому пользователю приходится угадывать последовательность «войти в Jira → вернуться → проверить», а при нескольких серверах — назначение отправки.

**Проще:** над таблицей показывать «Jira: host/context · пользователь · часовой пояс». Для auth-required — кнопка «Открыть Jira для входа», рядом «Проверить снова»; для неверного сервера — «Настройки Jira» с переходом к нужной секции. После смены глобальной конфигурации явно предложить применить новый контекст к текущему окну, сохраняя локальные строки. Базовый URL и timezone по-прежнему имеют одного владельца настроек; их не следует незаметно дублировать в двух формах.

**Зависимости:** `pages/worklog/worklog.html:20` (auth), `:73` (отправка), `worklog.js:73` (однократное чтение URL/TZ), `:512` (auth результат); `pages/options/options.html:315`/`:319`; `pages/popup/popup-jira.js:136` (открытие без контекста). Вход должен оставаться в настоящей Jira, запросы и timezone — в существующем `worklog-jira-client.js`; это улучшение навигации/обратной связи, а не перенос credentials в расширение.

## 5. Recorder: «Disable Cookies» скрывает выбор сессии и запускает отдельную настройку Chrome

**Путь:** Popup «Recorder» → «Открыть Traffic Recorder» → «Новая запись» → отмеченный по умолчанию «Disable Cookies» → при отсутствии доступа «Открыть настройки расширения» → включить incognito → Chrome перезапускает расширение → снова открыть Recorder → записывать и заново авторизоваться на сайте в чистом окне.

**Неудобство:** название обещает отключение cookies, но фактически cookies работают внутри запуска, а пользователь выбирает новый чистый профиль без текущей авторизации. Подсказка это объясняет, однако основной переключатель и его default сначала ведут по длинной цепочке настройки. Название секции «Параметры записи» также не сообщает, что те же switches управляют replay. Пользователь, желающий проверить текущую авторизованную сессию, должен сам сопоставить выключение «Disable Cookies» с нужным действием.

**Проще:** явный выбор «Сессия: текущая авторизация / чистая временная». Для чистой сессии показать «Потребуется повторный вход; нужен доступ incognito» и состояние разрешения до запуска. Заголовок «Параметры записи и перепроверки»; «Disable Cache» заменить понятным «Обходить кэш». Сохранить текущую защиту чистого режима и восстановление черновика после Chrome reload; не обещать автоматического обхода настройки incognito.

**Зависимости:** `pages/recorder/recorder.html:54`, `:57`, `:60`, `:65`; `recorder.js:477` (переход + draft); `recorder-settings.js:42`/`:44` (восстановление); `recorder-session-transport.js:116` (permission/другие incognito окна); `recorder-replay.js:220` и `recorder-session-controller.js:147` (одни параметры для record/replay). Предложение меняет описание выбора, не отменяет Chrome permission и не затрагивает обычные cookies.

## 6. Recorder: из результатов перепроверки нельзя непосредственно повторить перепроверку

**Путь:** «Запись и трафик» → «Открыть .dashflow» или запись → «Запустить replay» → автоматический переход в «Результаты перепроверки» → изучить изменения → для нового запуска снова «Запись и трафик» → «Запустить replay» → обратно в результаты.

**Неудобство:** основной цикл «изменил сайт → перепроверил → изучил → перепроверил снова» пересекает вкладки в обе стороны. В результатах есть только фильтры и «Экспорт Excel». Кнопка «К записи и трафику» существует лишь в пустом состоянии; после появления результатов она скрыта вместе с ним. Смешение слов «перепроверка» и `replay` заставляет искать другое название того же действия. В «Параметрах записи» не видно, что изменение режима сессии влияет на следующий replay.

**Проще:** в результатах добавить «Перепроверить ещё раз» и короткую сводку следующего запуска: сценарий, стартовый сайт, текущая/чистая сессия, кэш. Рядом — «Изменить параметры» с переходом в существующий блок. Использовать одно пользовательское название «Перепроверить сценарий»; технический `replay` можно оставить в пояснении. При запуске использовать тот же session owner и синхронный guard, не создавать второй обработчик lifecycle.

**Зависимости:** `pages/recorder/recorder.html:49`, `:166`, `:178`, `:186`; `recorder-view.js:258` (скрытие пустого блока), `:314` (comparison + переключение вкладки); `recorder-replay.js:220`/`:229` (режим/завершение). Две вкладки нужны для разных данных, но действие следующего запуска должно быть доступно рядом с результатом.

## Оправданные разделения, которые стоит сохранить

- **Popup → отдельные Batch/Recorder/Worklog pages.** Popup краткоживущий и слишком мал для таблиц/долгой операции. Убирать отдельную страницу ради сокращения одного клика не стоит. Можно улучшить launcher-контекст/подпись, но устойчивый документ и сохранение черновика важнее.
- **Batch settings page → собственное окно Grafana capture → PiP-прогресс.** Это owner-controlled окно с lease, захватом активной вкладки, отменой и cleanup. Оно не эквивалентно работе с текущей пользовательской Grafana. Упрощать нужно подготовку/сводку, не смешивать capture с чужой вкладкой.
- **Worklog local drafts и Jira transfer existing records.** Первая операция создаёт новые записи из локальной таблицы, вторая читает серверные записи и может удалять originals. Общая навигация «Учёт времени» полезна; одна неразличимая кнопка отправки/переноса — нет.
- **Recorder control page и контролируемое окно сайта.** CDP принадлежит конкретной сессии; закрытие страницы Recorder прекращает её. Чистое incognito-окно оправдано изоляцией и не должно превращаться в удаление cookies обычного профиля.
- **«Запись и трафик» и «Результаты перепроверки».** Baseline и replay не должны незаметно сливаться. Автопереход по готовности и отдельный Excel результата полезны; обратную цепочку исправляет повтор запуска на results, а не объединение таблиц.
- **Явный старт внешнего действия после выбора.** Автоматизировать read-only подготовку Batch можно; автоматически запускать capture/Jira POST/replay после импорта или выбора — нельзя. Подтверждение переноса и отдельное предупреждение о секретах `.dashflow` выражают реальные последствия.

## Приоритет

Начать с Jira transfer (однозначная отмена и обзор операции), затем Batch (единая область настроек и автоматическая подготовка) и контекста Jira в Worklog. Recorder session naming и повтор запуска из результатов — следующие небольшие улучшения. Это предложения следующего этапа, не повторный список уже исправленных F01–F12 и не заявка на изменение кода в этом аудите.
