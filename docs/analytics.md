# Обезличенная аналитика DashBridge

## Назначение и границы

Аналитика помогает приоритизировать поддержку функций у небольшой внутренней
аудитории. Она всегда включена, но собирает только псевдонимные агрегаты. На
клиенте запрещены IP-адреса, логины, имена, почта, URL и домены, названия
профилей/панелей, Jira keys и тексты, TDM/Recorder payload, содержимое буфера и
произвольные сообщения ошибок. Работающий сервер обязан также отключить access
logs с IP или настроить их немедленную анонимизацию.

«Обезличенная» здесь означает ограниченный payload без пользовательского
контента: UUID и история функций всё равно связывают события одной установки.
HTTPS endpoint и его proxy видят сетевой адрес при соединении; запрет относится
к сохранению IP в telemetry/логах, а не к отсутствию IP на сетевом уровне.

`installationId` создаётся локально через `crypto.randomUUID()` и сохраняется
отдельным ключом `dashbridgeInstallationId` в `storage.local`, независимо от
очереди событий. Перезапуск service worker, штатное обновление по прежнему пути
и миграция внутренней схемы сохраняют ID. Регистрации на сервере нет. Это
псевдоним, а не анонимность против владельца устройства: полное удаление
расширения/очистка browser storage или новый профиль создают новый ID, а
копирование профиля браузера может перенести прежний ID.

## Контракт события

Service worker принимает только объекты из статического каталога
`js/shared/analytics-contract.js`. Неизвестная функция, signal, dimension,
значение dimension или дополнительное поле отклоняются целиком.

Входы и владельцы: fail-open facade
[`analytics-client.js`](../js/shared/analytics-client.js), каталог
[`analytics-contract.js`](../js/shared/analytics-contract.js), sender guards
[`background.js`](../js/background.js), очередь и delivery
[`background-analytics.js`](../js/background-analytics.js). MAIN не имеет Chrome
API и сообщает закрытые actions через DOM event; isolated bridge переводит их
в разрешённые feature IDs, service worker повторно проверяет sender. Эта схема
ограничивает передаваемые поля, но событие страницы само по себе не доказывает
настоящий человеческий клик.

Сигналы имеют разный смысл:

- `used` — пользователь вызвал функцию;
- `changed` — изменил переключатель или режим;
- `configured` — функция сохранена в состоянии и может работать без новых кликов;
- `effective` — runtime подтвердил применение; одинаковое подтверждение хранится
  не чаще одного раза в день на installation/feature/dimensions;
- `outcome` — безопасная категория результата (`success`, `partial`,
  `cancelled`, `invalid_input`, `no_data`, `error` и т. п.);
- `lifecycle` — установка, обновление или дневная активность.

Сбой общей команды применения инструментов панели записывается один раз как
`internal.panel_tools_apply`, а не размножается по всем включённым функциям.
Dimension `failure` принимает только закрытые диагностические категории
(`runtime_dependency_missing`, `visual_verification_failed`,
`legend_apply_failed`, `timeout`, `unexpected_exception`). Текст исключения,
stack trace, URL и данные панели в аналитику не отправляются. Старые события без
`failure` нельзя достоверно классифицировать задним числом.

В очереди запись содержит только `eventId`, начало часа UTC, `featureId`,
`signal`, разрешённые dimensions, счётчик и версию расширения. Количества
пользовательских сущностей передаются только диапазонами `1`, `2_5`, `6_10`,
`11_plus`.

## Нагрузка и доставка

Минимальный интервал отправки действует и при большой накопленной очереди:
backlog не разрешает дополнительную пачку до следующего интервала.

События агрегируются по часу до записи. Extension pages используют один
делегированный обработчик `click` и `change`; snapshot читает уже существующий
storage не чаще раза в день и не обходит DOM/iframe/сеть. Очередь ограничена
2000 агрегатами, отправка — пачками до 100 не чаще раза в час, с
экспоненциальным backoff и восстановлением `inflight` после остановки MV3
worker. Периодический `chrome.alarms` имеет случайный начальный сдвиг; за один
wake-up отправляется не больше одной пачки, поэтому большой офлайн-хвост не
создаёт длительную фоновую передачу. Если очередь пуста, запроса нет. Ошибки
аналитики всегда fail-open для пользовательской функции.

Запись событий и фиксация результата отправки сериализуются отдельно от сети:
pending fetch не блокирует track. Один HTTP-запрос имеет AbortController и
deadline 15 секунд (конфигурация ограничена 1–25 секундами), с cleanup таймера.
Повтор и восстановление SW сохраняют неизменный inflight batch с теми же ID и
счётчиками: collector использует INSERT OR IGNORE, поэтому объединение уже
отправленного eventId с новыми кликами могло бы потерять их. Новые события
копятся отдельно; inflight входит в общий лимит очереди. Дневной snapshot
читает только profiles, Recorder settings и явный список sync-настроек;
Worklog/cache/diagnostic payload для него не читаются.

Production endpoint — `https://analytics.tongehub.com/v1/events/batch`.
Запрос отправляется без credentials и referrer и имеет вид:

```json
{
  "schemaVersion": 1,
  "installationId": "локально-созданный-uuid",
  "droppedAggregates": 0,
  "events": [
    {
      "eventId": "uuid",
      "periodStart": "2026-09-03T10:00:00.000Z",
      "featureId": "grafana.panel.fill_removed",
      "signal": "effective",
      "dimensions": { "surface": "dashbridge", "state": "enabled" },
      "count": 1,
      "extensionVersion": "2.4.3"
    }
  ]
}
```

Сервер по умолчанию хранит агрегаты 400 дней (`RETENTION_DAYS`, диапазон
30–1500 дней). Это настройка кода/Compose; фактическая конфигурация VPS
проверяется отдельно. Сырые HTTP-логи с IP не допускаются.

Collector [`server.js`](../deploy/dashbridge-analytics/server.js) принимает
публичный POST без регистрации/аутентификации установки: `validateBatch`
проверяет закрытый контракт, но не происхождение UUID. `readJson` ограничен
256 КиБ; общий `takeIngestToken` имеет burst 60 и восстанавливает один token
за 30 секунд без хранения IP. Это защита нагрузки, а не защита статистики от
поддельных событий; исчерпание общей квоты затрагивает всех клиентов. Порог
`MAX_DATABASE_MIB` (по умолчанию 512, минимум 64) останавливает новые записи с
HTTP 507 по оценке занятых SQLite pages и WAL, а не гарантирует точный размер
файла. `maintain` удаляет старые события при старте и ежедневно, делает WAL
checkpoint; внешние backups требуют собственной retention-политики.

Агрегация различает версии расширения. При восстановлении проверяются ID,
канонические даты часа, версии и счётчики; inflight ограничен 100 событиями,
общая очередь — 2000. Невалидные/лишние записи учитываются в droppedAggregates.
HTTP 400 переносит всю отклонённую пачку в локальный карантин (последние 100
событий); накопительный quarantinedCount сохраняет количество исключённых
агрегатов. Автоматической повторной отправки карантина нет. HTTP 401/403
помечается как configuration, 429/5xx и сеть повторяются; Retry-After ограничен
шестью часами и не обходит минимальный интервал. Серверный протокол учёта потерь
не менялся: при полностью дублированной пачке остаётся известное ограничение
подтверждения droppedAggregates.
Options показывает локальную очередь, старейшее событие, попытку, успех,
повтор и категорию ошибки без принудительной отправки и polling. Новых
telemetry-полей эти показатели не добавляют.

## Интерпретация отчёта

Охват функции — уникальные установки с любым выбранным сигналом, делённые
на установки с сигналами в том же периоде и контексте без фильтра функции и
сигнала. Это наблюдение функции, а не число людей или доказанных вызовов.
`configured` — исторический снимок, `effective` — подтверждение применения;
общий apply не доказывает фактическое срабатывание уведомления. Дочерняя
настройка учитывается только при включённом родителе. Prepared capture
подтверждается владельцем снимка. Время и fullscreen регистрируются только
своими контроллерами; открытие редактора отчёта не означает сохранение.

Неподдерживаемый сигнал обозначается «—», отсутствие outcome — «Нет
результатов». Период включает выбранное число календарных дней UTC, текущий
день неполный; нули означают отсутствие полученных сигналов. При периоде
более 60 дней график суммирует сигналы по группам из семи дней, а точная
дневная таблица сохраняется. Уникальные установки по дням не суммируются.
Исторические дубли и ложные подтверждения не исправляются предположительно.

Options показывает местное время и нижнюю границу следующей попытки:
фактическое выполнение зависит от alarm и доступности браузера/сети.
Протокол приёма, состав telemetry-полей и очередь остаются прежними.

## Добавление события

Сначала добавьте стабильный `featureId`, signals и закрытый набор dimensions в
контракт. Затем вызывайте только `DashBridgeAnalytics.track/opened/changed` или
`outcome`. Нельзя передавать динамические строки даже под новым нейтральным
именем поля. Для сохранённых функций добавьте безопасный дневной snapshot, а
для runtime-функций — коррелированное подтверждение от владельца применения.
Обязательны отрицательные тесты на лишние поля и чувствительные значения.

## Изоляция тестовых запусков

Browser smoke всегда создаёт новый временный профиль Chromium, поэтому не
должен обращаться к production collector: иначе каждый прогон выглядел бы как
новый анонимный пользователь. Runner загружает временную копию расширения и
меняет endpoint только в этой копии на локальный HTTP-приёмник `127.0.0.1`.
Так проверяется реальная отправка из service worker без изменения DNS,
production-конфигурации или сетевого поведения пользовательского расширения.

Live E2E, auth/session-check, desktop geometry и корневой `Запустить Grafana Playwright.cmd`
загружают исходное расширение, поэтому блокируют `analytics.tongehub.com`
на уровне отдельного процесса браузера: `--host-resolver-rules` возвращает
`~NOTFOUND`, а `--no-proxy-server` запрещает manual proxy и PAC/WPAD, которые
могли бы разрешить имя удалённо. Это прямое соединение только для тестового
браузера, не изменение системного proxy. Если Grafana доступна исключительно
через HTTP/SOCKS proxy, нужен отдельный staged-режим с локальным/пустым endpoint;
снимать flags с обычного тестового профиля нельзя.
Node-launchers используют `testBrowserNetworkArgs` из
`scripts/setup-grafana-e2e-profile.js`; PowerShell-launcher передаёт ту же пару
аргументов и отказывается переиспользовать CDP-окно без подтверждённых flags.
Уже открытый старый тестовый браузер нужно закрыть и запустить заново.
Системные DNS/hosts, обычный пользовательский Chrome и release не изменяются.
Админку аналитики в этом тестовом браузере также открыть нельзя.

Это блокировка доставки, а не отключение сбора: ограниченная очередь и backoff
продолжают работать локально. Тестовый профиль нельзя позже запускать без этих
аргументов или переносить в рабочий: накопленная очередь тогда может отправиться.
`test/analytics_test_browser_behavior.js` проверяет реальный Chromium, extension
worker и страницу при manual/PAC proxy configuration: collector не достигает
даже локального proxy, а обычный прямой HTTP остаётся доступен.

При согласованном полном сбросе статистики очищаются таблицы `events` и
`service_metrics` в одной SQLite-транзакции, после успешной согласованной копии
через `VACUUM INTO`. Файл базы, схема и индексы сохраняются; restart не нужен.
Удалять файл работающей WAL-базы нельзя. Сброс сервера не очищает очереди
клиентов: рабочие установки могут прислать накопленные события после сброса.

## Разработка и публикация collector

Локальная админка использует отдельную синтетическую SQLite и loopback-only
dev gateway. `scripts/Start-AnalyticsDev.ps1` запускает её в Node watch; с
production endpoint и `/data` этот режим не связан.

Production использует постоянный `node:24-alpine` с read-only bind mount кода,
а не сборку application image. Административные assets читаются на каждый
запрос, поэтому HTML/CSS/client JS применяются без остановки ingestion.
Публикация backend выполняет проверенную загрузку, backup, короткий restart,
health-check и rollback; SQLite находится в отдельном `/data` и не входит в
release. Compose и root helper не обновляются через ограниченный deploy-канал.

Админка доверяет `X-DashBridge-Admin` после bcrypt в Caddy (`requireAdmin`),
поэтому отсутствие host port и доступ к Docker-сети входят в границу доверия.
Внешний клиентский header должен удаляться/заменяться proxy, как в
[`deployment README`](../deploy/dashbridge-analytics/README.md). Контейнер в той
же сети может обратиться к backend с этим header напрямую; это не второй
уровень проверки пароля приложением. Авторизованный deploy-пользователь может
менять код приложения, хотя release не принимает Compose/root helper.

Отрицательные проверки полей и восстановления доставки:
[`analytics_contract_behavior.js`](../test/analytics_contract_behavior.js),
[`analytics_delivery_recovery_behavior.js`](../test/analytics_delivery_recovery_behavior.js),
[`background_analytics_behavior.js`](../test/background_analytics_behavior.js) и
[`analytics_static_privacy_behavior.js`](../test/analytics_static_privacy_behavior.js).
Приём/dedup/auth/report проверяет
[`server.test.js`](../deploy/dashbridge-analytics/test/server.test.js);
race результатов admin UI —
[`admin-race.test.js`](../deploy/dashbridge-analytics/test/admin-race.test.js).
